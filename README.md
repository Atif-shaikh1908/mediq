# MediQ

MediQ is a Vite application backed by Supabase Auth, Postgres, Row Level Security, and Realtime. Application records are not stored in `localStorage`; Supabase Auth persists the staff session using its supported browser session handling.

## Supabase setup

1. Create or select a Supabase project and configure email/password authentication. Disable public sign-ups; staff accounts should be invited by a trusted administrator.
2. Apply the migrations in order: [`202611190001_mediq_core.sql`](./supabase/migrations/202611190001_mediq_core.sql), [`202611190002_revoke_trigger_function_execute.sql`](./supabase/migrations/202611190002_revoke_trigger_function_execute.sql), and [`202611190003_india_queue_timezone.sql`](./supabase/migrations/202611190003_india_queue_timezone.sql). The core migration expects the standard `supabase_realtime` publication. It creates departments and the default hospital name, enables RLS, defines the queue RPCs, and adds the queue tables to Realtime. Apply [`202611190004_public_registration.sql`](./supabase/migrations/202611190004_public_registration.sql) only after its SQL has been reviewed and approved.
3. In Supabase Auth, invite the first administrator. In the SQL editor, provision that Auth user as MediQ's first staff profile (replace the email and name):

   ```sql
   insert into public.staff_profiles (user_id, email, full_name, role)
   select id, email, 'MediQ Administrator', 'Admin'
   from auth.users
   where email = 'admin@your-hospital.example'
   on conflict (user_id) do nothing;
   ```

4. Provision subsequent staff Auth accounts using Supabase Auth invitations, then create each `staff_profiles` row from the SQL editor or as an administrator using an approved server-side provisioning workflow. The browser intentionally does not create Auth users or hold a service-role key.
5. Copy `.env.example` to `.env` (or `.env.local`) and set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the project's API settings. Vite requires the `VITE_` prefix; a legacy `VITE_SUPABASE_ANON_KEY` is accepted, but a secret/service-role key is never used by this app.
6. Restart Vite after changing environment variables:

   ```sh
   npm run dev
   ```

The app stays on a setup screen when Supabase environment variables are missing. It does not seed fallback patient/staff data. The anonymous `/display` route reads only `public_queue_display`, which contains department names and queue tokens, not patient IDs, names, phone numbers, or priorities. The public `/register` route remains non-submitting unless `VITE_PUBLIC_REGISTRATION_ENABLED=true`; only enable it after the public Edge Function and its database migration have both been deployed and tested.

## Public patient registration

The public form calls the `public-register` Edge Function; it never calls the authenticated staff `register_patient` RPC. The function is configured for anonymous HTTP requests, validates and normalizes every field, checks an exact-origin CORS allowlist, limits the request body, applies a database-backed limit of 30 HTTP attempts per client fingerprint in a rolling 10-minute window (including invalid submissions; CORS preflight is exempt), and uses a retained idempotency key to replay a prior result instead of creating a duplicate. It returns only the generated Patient ID and token. It does not expose a patient-record read route.

Before enabling `VITE_PUBLIC_REGISTRATION_ENABLED`, apply the reviewed public-registration migration and deploy `supabase/functions/public-register`. Configure `PUBLIC_REGISTRATION_ORIGINS` and a random `PUBLIC_REGISTRATION_HASH_SECRET` of at least 32 characters as Edge Function secrets. Supabase's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are consumed server-side only; never put the service-role key in Vite environment variables or browser code. The function trusts the platform-provided client-IP headers for rate-limit fingerprinting; verify the deployed gateway's header behavior before enabling public traffic. The database migration and Edge Function are staged locally and have not been applied or deployed.

## Permissions and data behavior

- Admin and Receptionist can register patients and edit patient profiles.
- Admin, Doctor, and Nurse can set clinical priority and complete a serving visit.
- All active staff can call the next patient; PostgreSQL serializes calls per department/day and orders by the authorized priority, then arrival.
- The database assigns daily department tokens using `Asia/Kolkata` and enforces uniqueness. The patient identifier is generated by Postgres.
- Only Admin can update staff roles and hospital settings or read audit logs.
- Patient profile, visit, queue, and staff data require an authenticated active staff profile and are protected by RLS. Sensitive writes use role-checked database policies or RPC functions.
- Queue changes are synchronized to authenticated clients via Supabase Realtime. The separate public display table contains only the currently serving and next tokens for each department.

## Security notes

The browser publishable/anon key is public by design; RLS is the security boundary. Do not put database passwords, Supabase secret keys, or service-role keys in `.env`, Vite variables, or browser code. Review and test policies in a non-production project before using any real patient information. This application does not provide clinical decision support.

The linked project’s Security Advisor no longer reports anonymous access to trigger-only `SECURITY DEFINER` functions. It still reports authenticated access to the role-checked queue RPCs and role helper; test those permissions with each staff role before production use.

## Known gaps

- Staff Auth invitations and initial profile provisioning are administrator-operated in Supabase; the app does not include a trusted server/Edge Function to invite users.
- No production deployment, email delivery, organization/tenant isolation, backup/retention policy, or penetration/security test is configured here.
- UI reporting loads records from the current Supabase dataset and is intended for a single hospital project. For a large deployment, add server-side pagination and date-filtered reporting queries.
- The linked project has the core schema and function-permission hardening migrations applied, but no staff Auth user or profile has been provisioned. Authenticated role flows still need testing with staff accounts before real patient information is used.
- The linked database already reports `Asia/Kolkata` for queue-date calculations, but its migration history does not show the local timezone migration. Reconcile that history before applying later migrations; public-registration migration 004 is a local draft only.
